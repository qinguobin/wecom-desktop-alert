# 实测记录 01 · 企业微信消息读取通道的四条路

目标：证明"能否在不操作鼠标键盘的前提下，自动读到企业微信里别人发来的消息"。

结论先行：**只有「屏幕 OCR」一条路可用，且企微窗口必须真实显示在屏幕的「消息」页。**

---

## 路径一：客户端 UI 自动化（UIA）—— ❌ 死路

企业微信是 **Flutter 渲染**，Flutter 默认不向 Windows 的 UI Automation 暴露无障碍树。

```
企微主窗口 class = WeWorkWindow
  └─ 唯一子窗口 class = FLUTTERVIEW
      └─ UIA 遍历结果：只有 2 个节点，Name 均为空
```

复现脚本：`tools/probe_windows.py`

直接后果：
- 读不到任何一条聊天文本；
- 也点不动任何会话（"右键 → 标记为已读"这类操作无从下手）；
- 后面"勾掉后消角标"只能改走快捷键路线。

---

## 路径二：官方连接器（`wecom-cli` 1.3.4）—— ❌ 死路（企业层未开通）

连接器本身是通的（`auth show --status` → `authorized`），但读消息的接口被拦在企业层。

```
$ wecom-cli chat messages list --chat-id 秦国彬  → errcode 853006
$ wecom-cli chat messages list --chat-id wmXXXX  → errcode 853006
$ wecom-cli chat messages list --chat-id <机器人ID> → errcode 853006
$ wecom-cli chat messages list --chat-id test    → errcode 853006
$ wecom-cli chat groups list                     → errcode 853006
```

**关键推理**：4 个 ID 里有 3 个是瞎编的（`wmXXXX` / `test`），却返回同一个错误码，
说明拦截发生在**校验 chat-id 之前**，是**企业层级的功能开关**，不是参数问题：

```
this tool is not available for your corporation
```

通讯录接口同样被拦：

```
$ wecom-cli contact users search --keywords "秦"  → errcode 850002
```

**全量普查**（证明没有任何"收消息"命令存在）：

```
wecom-cli message recv      → unrecognized subcommand
wecom-cli message receive   → unrecognized subcommand
wecom-cli message pull      → unrecognized subcommand
wecom-cli message list      → unrecognized subcommand
wecom-cli message aibot recv → unrecognized subcommand
wecom-cli chat recv         → unrecognized subcommand
wecom-cli webhook           → unrecognized subcommand
wecom-cli callback          → unrecognized subcommand
```

唯一能正常返回的读类接口是 `message aibot sessions list`，但它只返回**机器人自己**
会话的**元数据**，且当前为空，**没有任何命令能读这些会话的消息正文**：

```json
{"sessions_count": 0}
```

> 顺带的坑：`wecom-cli` 只在 Git Bash 的 PATH 里，Windows 原生环境找不到，
> 从 Python subprocess 调用必须写完整路径 `…\cli-connector-packages\wecom-cli.cmd`。

**结论：连接器能发不能收。想让它能读，需企业管理员开通「会话内容存档」。**

---

## 路径三：Windows 系统通知（Toast）—— ❌ 死路（本机企微根本不弹）

企微的通知是系统层渲染的，理论上不受 Flutter 限制，能被 UIA 捕获。实测：

```
tools/probe_toast.py    运行 180 秒 → 0 条
tools/probe_toast2.py   运行 240 秒 → 0 条
tools/probe_toast2.py   运行 150 秒 → 0 条
```

150～240 秒内企微**一个通知窗口都没弹过**。（前提是用户确实在此期间发了消息。）

之前还试过直接解析 Windows 通知历史库 `%LOCALAPPDATA%\…\wpndatabase.db`（ESE 格式），
但 `pyesedb` 编译装不上，这条路也断了。

---

## 路径四：屏幕截图 + OCR —— ⚠️ 可用，但有硬边界

**这是唯一走通的路。** 原理：Flutter 虽然不暴露控件树，但它最终要把像素画到窗口上。

### 关键突破 1：用 `PrintWindow` 而非 `BitBlt`

一开始用 `BitBlt` 抓窗口，抓到的是**过期帧**（画面永远停在若干分钟前），
这是"用户发了消息、程序毫无反应"的直接原因。

原因是 Flutter 走 DirectComposition 合成，普通 DC 拷贝拿不到当前内容。
改用 `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)` **强制重渲染**后才拿到真实画面。

```python
PW_RENDERFULLCONTENT = 2
ok = user32.PrintWindow(hwnd, mem, PW_RENDERFULLCONTENT)
if not ok:
    gdi32.BitBlt(mem, 0, 0, w, h, hdc, 0, 0, SRCCOPY)   # 回退
```

### 关键突破 2：OCR 前先放大 2 倍

Windows OCR 对 12px 小字识别率很差。用 GDI `HALFTONE` 模式高质量放大 2 倍后，
识别质量可用（人名偶有误差，消息正文基本准确）。

```python
gdi32.SetStretchBltMode(mem2, HALFTONE)
gdi32.SetBrushOrgEx(mem2, 0, 0, 0)
gdi32.StretchBlt(mem2, 0, 0, W, H, mem, 0, 0, w, h, SRCCOPY)
```

引擎用 Windows 自带的 `Windows.Media.Ocr`（`winsdk` 包），本机中文语言包可用：

```
available OCR languages: [... 'zh-Hans-CN' ...]
```

> 坑：WinRT 的 `IAsyncOperation` 不能自己造 event loop 去 await，
> 要用事件驱动的方式同步等待，否则卡死。

> 另一个坑：Pillow 装不上（网络/编译问题），索性用标准库 `zlib` + `struct`
> 手写 PNG 编码，零依赖。

### 硬边界：企微一旦"看不见"，画面就冻结

这是最要命的发现，用内容指纹（对 OCR 行做 md5）做的受控实验：

| 企微窗口状态 | 现象 | 结论 |
|---|---|---|
| 正常显示在屏幕 | 指纹随新消息变化 | ✅ 可用 |
| **最小化到任务栏** | 用户发消息后 70 秒，指纹纹丝不动 | ❌ 冻结 |
| **移到屏幕外**（未最小化） | 2.5 分钟无变化；移回屏幕内**立刻**变化 | ❌ 冻结 |
| 切到「工作台/文档」页 | 没有会话列表可识别 | ❌ 无内容 |
| 被其它窗口完全盖住 | 仍可读（PrintWindow 强制重渲染） | ✅ 可用 |
| 在另一个虚拟桌面 | 仍可读 | ✅ 可用 |

结论：**企微必须"真的显示在屏幕上"，且停在「消息」页**。
被别的窗口盖住没关系（这是好消息——可以把它藏在后面）。

所以"企微最小化也能实时读到"这个最初的判断是**错的**，后来被推翻。
